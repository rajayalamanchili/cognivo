# Phase 0 Research: Learner Dashboard

No item in Technical Context was marked `NEEDS CLARIFICATION` -- this
feature's platform, language, storage, and testing choices are already
locked by `tech-stack.md` and already implemented in `backend/` and
`frontend/` from Milestones 1-2. Research here is scoped to the
feature-specific design decisions the spec's Clarifications didn't
already pin down.

## 1. "Upcoming topics" reuses the Sequencing Agent's existing ranking

**Decision**: FR-003's "up to 3 likely upcoming topics" are the next
entries, in order, of the same eligible-topic ranking
`select_next_topic` already computes to pick the single top-priority
topic (lowest `p_mastery` first, `unknown` treated as lowest,
`order_index` as tiebreak -- `agents/sequencing/agent.py`'s existing
`_sort_key`). The eligibility/ranking computation is extracted into a
shared private helper so both the existing `select_next_topic` (used by
the real next-question flow) and a new `preview_topic_priority`
(dashboard-only) call the identical logic -- the fallback case (zero
eligible topics) reuses the same `mastered`-topics-or-all-topics pool
`select_next_topic` already falls back to, so a dashboard for a learner
who has mastered everything shows a coherent preview rather than an
empty one.

**Rationale**: Spec.md FR-003 explicitly requires the upcoming-topics
list be "generated by consulting the Sequencing Agent's actual selection
logic ... not a separately invented ordering." Reusing the exact ranked
list (items 2-4, after the chosen item 1) is the only implementation
that satisfies that requirement by construction -- a second, independently
designed "likely next" heuristic (e.g. a breadth-first walk of
`PrerequisiteEdge` successors) would inevitably diverge from what the
Sequencing Agent would actually pick if asked repeatedly, which is
exactly the "separately invented ordering" FR-003 rules out.

**Alternatives considered**: A `PrerequisiteEdge`-successor graph walk
from the chosen topic (topics that depend on it). Rejected: successors
becoming *unlockable* is a different question from what the Sequencing
Agent would *actually rank highest* next (a successor's other
prerequisites might still be unmet, or a lower-`order_index` unrelated
topic might rank higher by the real selection rule) -- building this
would be a second, competing "next" algorithm, undermining FR-003's
own requirement rather than satisfying it.

## 2. No new agent, no LLM/ADK call

**Decision**: All three dashboard sections are pure composition of
already-computed, already-deterministic data -- no `LlmAgent`/`LiteLlm`
call anywhere in this feature, and no new ADK-registered agent boundary.

**Rationale**: Spec 002's research.md §1 already flagged this exact
question and forward-referenced it here: "[an LLM-generated narrative
report] can be revisited ... as part of the Learner Dashboard, Milestone
4, if a real product need for prose summaries emerges -- at which point
it would need its own grounding discipline analogous to FR-011, not a
silent addition here." Nothing in this feature's spec.md FRs or SCs
requires generated prose; FR-002 requires the Recommendation Agent's
existing structured output displayed "verbatim." Adding an LLM call the
spec doesn't require would be scope creep the Constitution's own
Principle IV (agent boundaries reflect real responsibility) and
Principle I (no LLM guessing) both argue against introducing casually.

**Alternatives considered**: An LLM-generated one-paragraph dashboard
summary tying the three sections together. Rejected for the reason
above; if a future milestone wants this, it needs its own spec-level
grounding requirement, not an incidental addition here.

## 3. New topic-priority-preview endpoint writes no audit event, no trace

**Decision**: `GET /api/learners/{learner_id}/topic-priority-preview`
writes no `AssessmentEvent` row and is not wrapped in `traced_request()`
-- it makes no LLM/ADK invocation (nothing for `GoogleADKInstrumentor`
to instrument) and, more importantly, it does not represent a real
pedagogical decision being committed to the learner.

**Rationale**: The existing `next_topic_selected` event type (written by
`generate_next_question`) means "this topic was actually chosen and a
question was generated for it" -- a real "why was I shown this" moment
per Constitution Principle V. The dashboard's path-visualization preview
is explicitly illustrative and non-committing (spec.md FR-004): a
learner may load the dashboard many times without ever answering
another question. Logging a `next_topic_selected` event on every
dashboard load would flood the audit log with events describing
decisions that were never actually acted on, actively undermining
Principle V's "traceable to a specific ... decision" requirement rather
than satisfying it. This matches the existing `GET /mastery-state`
precedent (also a pure, untraced, unlogged read).

**Alternatives considered**: A new `topic_priority_previewed` event
type, logged but distinct from `next_topic_selected`. Rejected as
unnecessary for this milestone -- no FR or SC requires an audit trail of
dashboard views themselves (unlike the Recommendation Agent's FR-008,
which is explicit), and every dashboard load already multiplies
`recommendation_report_generated`/`weak_area_flagged`/
`next_step_suggested` writes (§5 below) without complaint from any SC;
adding a fourth per-load event type for a preview nobody asked to audit
would be growth without a stated requirement.

## 4. New `GET /api/subjects` endpoint

**Decision**: A new, minimal endpoint lists every `Subject` with
`validated_at IS NOT NULL` (`subject_id`, `display_name`), mirroring the
existing `_get_validated_subject` gate already used by
`api/routes/recommendation.py` and `api/routes/mastery.py`.

**Rationale**: This feature's Clarifications require the dashboard to
render one section per subject with a content artifact in the platform,
including subjects the learner has zero engagement with (User Story 4 /
FR-005). No existing endpoint returns "the platform's list of usable
subjects" -- every current endpoint takes `subject_id` as an input, none
enumerates them. Without this, the frontend would have no
non-hardcoded way to discover which sections to render, silently
breaking SC-005's "zero engine-code changes" extensibility bar the
moment a third subject is added (a hardcoded `["algebra-1", "biology"]`
list in the frontend would itself be exactly the kind of hardcoding
Constitution Principle III prohibits).

**Alternatives considered**: Hardcoding the two known subject ids in the
frontend. Rejected for the SC-005/Principle III reason above.

## 5. Three independent per-subject fetches, not one aggregate endpoint

**Decision**: The frontend issues three independent HTTP calls per
subject (existing mastery-state, existing recommendations, new
topic-priority-preview) rather than the backend exposing one aggregate
`GET /api/learners/{learner_id}/dashboard` endpoint.

**Rationale**: FR-007 and FR-008 both require that a failure in one
section (weak-area report, or path visualization respectively) never
prevents the other sections of the same subject from rendering. Three
independently-awaited fetches give this for free -- each promise
resolves or rejects on its own, and the frontend renders each section's
own phase independently (mirroring `mastery-flow.tsx`'s existing
loading/loaded/error pattern, applied three times per subject instead of
once). A single aggregate backend endpoint would have to either fail
all-or-nothing per subject (violating FR-007/FR-008 outright) or
reinvent partial-failure response modeling (a per-field
success/error-code envelope) that three plain REST calls already
provide as a natural consequence of being separate requests -- an
aggregate endpoint would be solving a problem the existing endpoint
shape doesn't have, for no benefit this feature's spec actually asks
for.

**Alternatives considered**: A single `GET /dashboard?subject_id=X`
aggregate endpoint returning all three pieces in one response, with a
per-field `status: "ok" | "error"` envelope. Rejected as unnecessary
complexity given the independent-fetch approach already satisfies
FR-007/FR-008 using the existing, unmodified endpoint contracts plus
one new thin one -- revisit only if a future milestone needs to reduce
the two-subject platform's 6-calls-per-load count for a real, measured
latency reason (`tech-stack.md`'s "Explicitly not yet decided" Fluid
Compute entry sets the precedent for deferring this kind of
optimization until a real number motivates it).

## 6. Repeated `AssessmentEvent` writes on every dashboard load

**Decision (not a new decision, restated for this feature's context)**:
Per FR-002, each dashboard load triggers a fresh, subject-scoped
`/recommendations` call, which -- per spec 002's existing, unmodified
FR-008 -- writes a new `recommendation_report_generated` event plus one
`weak_area_flagged`/`next_step_suggested` pair per flagged topic, every
time. A learner who reloads the dashboard 20 times in a session
produces 20x the audit-log volume that a single explicit "show me my
weak areas" request would have.

**Rationale for not changing this now**: Spec.md's own FR-002
("MUST trigger a fresh Recommendation Agent report ... not a cached
one") and FR-006 (no caching, consistent with Milestone 1's statelessness
requirement) already made this tradeoff explicitly, and no SC in this
feature or spec 002 caps audit-log volume. Recording it here so a future
milestone doesn't rediscover this as a surprise: if audit-log volume
ever becomes an operational concern, the fix belongs in spec 002's
`AssessmentEvent` design (e.g. a `RECOMMENDATION_REPORT_GENERATED`
dedup window), not in this feature, which is correctly just a consumer
of that existing contract.
