# Data Model: Grade-Banded Curriculum Scoping

**Feature**: `017-grade-banded-curriculum` | **Date**: 2026-09-06

Two new tables, two modified tables, three new `AssessmentEventType`
values. All additions are nullable/opt-in per `research.md` Decision 1
-- an ungraded subject's rows are entirely unaffected.

## New: `GradeBand` (`backend/src/models/grade_band.py`)

The 1-12 grade-level entity FR-001 resolved to: a grouping layer above
`Topic`, authored per subject, never an engine-side conditional.

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `subject_id` | `str` (FK -> `subjects.subject_id`) | No | Composite PK (part 1). |
| `grade` | `int` | No | Composite PK (part 2). `CHECK (grade BETWEEN 1 AND 12)`. |

No other columns (`research.md` Decision 9). `UniqueConstraint` is
implicit in the composite PK. A subject with zero `GradeBand` rows is
fully ungraded (FR-009); one with any `GradeBand` rows requires every
`Topic` to declare a `grade` (Decision 1) -- enforced by
`services/content_artifact/validator.py`, not a DB constraint (the same
place `difficulty_calibration`/`misconceptions` schema rules already
live).

## Modified: `Topic` (`backend/src/models/topic.py`)

One new nullable column:

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `grade` | `int` | Yes | `NULL` for every topic in an ungraded subject (Decision 1). `ForeignKeyConstraint(["subject_id", "grade"], ["grade_bands.subject_id", "grade_bands.grade"])` when set. |

**Grade-entry topic** (Decision 2, derived, not stored): topic `t` in a
graded subject is a grade-entry topic iff
`all(prereq.grade < t.grade for prereq in t.prerequisites)` (vacuously
true when `t.prerequisites` is empty). For the subject's lowest declared
grade this is identical to `is_entry_level`'s existing "zero
prerequisites" rule, since no grade exists below the lowest one.
`is_entry_level` itself is unchanged and continues to gate ungraded-
subject placement exactly as today.

## New: `LearnerGradeProgress` (`backend/src/models/learner_grade_progress.py`)

The "one explicit current starting/unlocked grade value per subject per
learner" spec.md's Key Entities describes as an extension of
`MasteryState` -- modeled as its own table (composite PK is per-learner-
per-subject, not per-topic like `MasteryState`) rather than a new column
on it.

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `learner_id` | `UUID` (FK -> `learner_profiles.learner_id`) | No | Composite PK (part 1). |
| `subject_id` | `str` (FK -> `subjects.subject_id`) | No | Composite PK (part 2). |
| `unlocked_grade` | `int` | No | Set once at placement (the starting grade, FR-003), then only ever increased (FR-004/FR-005), never decreased -- see Edge Cases below. |
| `updated_at` | `DateTime(timezone=True)` | No | `server_default=func.now()`, updated on every write. |

**Row lifecycle**: created once, at the end of `submit_placement`, for
any subject with `GradeBand` rows (skipped entirely for an ungraded
subject -- no row is ever created, matching FR-009). Updated in place
only by `apply_mastery_update`'s unlock check (`research.md` Decision
7), and only upward.

**Monotonicity (Edge Cases)**: `unlocked_grade` is a high-water mark, not
a derived-at-read-time value like `MasteryState.band`. If it were
recomputed live from current mastery state, a later mastery regression
on a lower grade's topic would revoke access already granted --
explicitly disallowed by spec.md's Edge Cases ("already-unlocked grades
stay unlocked"). Storing and only-increasing it is what makes that
guarantee hold structurally rather than by convention.

**No row yet, for a graded subject**: only possible if a learner
attempts to answer a graded subject's question before ever completing
its placement flow -- not a reachable path through the existing
API (Milestone 1's `start_placement` is the only entry point that
creates `GeneratedQuestion` rows for a subject a learner hasn't yet
started), so the Sequencing Agent's eligibility filter treats a missing
row defensively as `unlocked_grade = min(declared grades)` (the most
conservative floor) rather than raising.

## Modified: `GeneratedQuestion` (`backend/src/models/generated_question.py`)

Two new nullable columns:

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `grade` | `int` | Yes | The grade label shown to the learner (FR-002), copied from `Topic.grade` at generation time. `NULL` for an ungraded subject's questions, unchanged from today. |
| `placement_session_id` | `UUID` | Yes | Mirrors the existing `quiz_session_id` column's role for quiz questions (`research.md` Decision 5). Set only for questions generated by `start_placement` or the new skip endpoint; `NULL` for practice/quiz questions, unchanged from today. |

## Modified: `AssessmentEventType` (`backend/src/models/enums.py`)

Three new members, added via one Alembic enum-extension migration
(matching the existing `misconception_classified`/quiz-assignment
enum-addition precedent -- one small migration per prior enum
extension, not folded into the schema migration):

| Member | Value | Emitted by | Payload |
|---|---|---|---|
| `GRADE_ASSIGNED` | `"grade_assigned"` | `submit_placement`, once, only for a graded subject | `{"starting_grade": int, "placement_session_id": str, "correct_by_grade": {str(grade): bool}}` |
| `GRADE_UNLOCKED` | `"grade_unlocked"` | Whichever of `placement.py`/`questions.py` receives a non-null `MasteryUpdateResult.grade_unlocked` | `{"previous_unlocked_grade": int, "new_unlocked_grade": int, "triggering_topic_id": str}` |
| `PLACEMENT_QUESTION_SKIPPED` | `"placement_question_skipped"` | The new skip endpoint | `{"skipped_question_id": str, "skipped_topic_id": str, "skipped_grade": int, "replacement_question_id": str \| None, "replacement_topic_id": str \| None, "replacement_grade": int \| None, "placement_session_id": str}` |

`GRADE_ASSIGNED`/`GRADE_UNLOCKED` together are FR-010's audit-log
requirement; `PLACEMENT_QUESTION_SKIPPED` is what lets Acceptance
Scenario 4 of User Story 1 ("the system can state which answers drove
that placement") account for a skip, not just the questions that were
actually answered.

## `MasteryUpdateResult` (`backend/src/agents/sequencing/mastery_tool.py`, modified)

One new field: `grade_unlocked: int | None = None`. Non-null only on the
specific `apply_mastery_update` call whose posterior update completed a
grade band's mastery requirement and a next declared grade exists to
unlock (`research.md` Decision 7). `None` in every other case, including
when the topic is ungraded, when the completed grade has no next grade
(subject's grade-progression is complete, User Story 2 Acceptance
Scenario 3 -- reported by simply never unlocking further, not by a
separate flag), or when the completing topic's grade isn't the
learner's *current* `unlocked_grade` (already-completed-earlier-grade
edge case, not expected in practice given monotonic gating, but not
assumed impossible either).

## Migrations

Two new Alembic revisions, both additive-only:

1. Schema: `grade_bands` table, `topics.grade` + FK, `generated_questions.grade` + `generated_questions.placement_session_id`, `learner_grade_progress` table. No backfill -- every existing row predates this feature and is correctly represented by `grade IS NULL` / no `LearnerGradeProgress` row.
2. Enum: the three new `AssessmentEventType` values above (`ALTER TYPE ... ADD VALUE`, matching the existing enum-extension migrations' shape).
