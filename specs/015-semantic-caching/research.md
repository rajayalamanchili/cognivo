# Phase 0 Research: Semantic Caching

## §1. Cache storage mechanism

**Decision**: Two new PostgreSQL tables in the existing Neon database (`question_generation_cache`, `grading_response_cache`), the grading table using the already-installed `pgvector` extension for similarity search. Resolves `tech-stack.md`'s "Semantic-caching layer (in-database via Postgres, or a dedicated cache like Redis/Upstash) -- Milestone 13 decision."

**Rationale**: Every other piece of this project's persistent state already lives in the same Neon Postgres database, accessed from the same stateless Vercel Functions (Constitution Principle IX -- no persistent process, no in-memory cache assumed to survive between invocations). `pgvector` is already an installed extension and column type (`content_passage_embedding.py`'s `Vector(1024)`) used for exactly this kind of embedding-similarity lookup, just for a different purpose (Tutor retrieval, Milestone 9). Adding Redis/Upstash would be a genuinely new dependency, a new environment variable, a new failure mode to handle, and a new connection-pooling story on serverless -- for a capability Postgres already provides at the scale this milestone targets (bounded pool size for question-gen; a single indexed table for grading). Ladder rung 2 (already in this codebase) beats rung 5 (a new dependency) here.

**Alternatives considered**: Redis/Upstash -- rejected, no concrete need stated that Postgres can't meet, and it would be the first cache-shaped external dependency this project has ever needed to reason about failure modes for (connection limits, eviction policy, a second thing that can be down). Vercel KV -- same rejection, plus it's edge-KV shaped (simple get/set), not a natural fit for `pgvector` cosine-distance queries the grading cache needs.

## §2. Question-generation cache lookup

**Decision**: A new `get_or_generate_question(db, *, subject_id, topic_id, difficulty, content_version, generation_prompt_version, avoid_stems, ...) -> tuple[GeneratedQuestionDraft, CacheOutcome]` in `backend/src/services/question_cache/cache.py`, called from both `sequencing/agent.py`'s and `quiz/session.py`'s existing retry loops in place of their direct `generate_question(...)` call. Logic: query `question_generation_cache` rows matching the exact key tuple with `created_at > now() - 24h`, excluding any row whose `stem` is a near-duplicate of `avoid_stems` (reuses `services/dedup/checker.py::is_near_duplicate`, same 0.85 threshold, so the pool respects the *same* per-learner exclusion the existing retry loop already enforces) -- if any remain, pick one at random and return it as a hit; otherwise call `generate_question(...)` for real, validate it (existing `_validate_draft`), insert it into the pool, delete the oldest row for that key tuple beyond the 5th, and return it as a miss.

**Rationale**: This slots into the *existing* retry loop structurally rather than replacing it -- the loop already does "generate a candidate, check `is_near_duplicate`, retry if not"; caching just changes where the candidate comes from on each iteration. No change to `persist_quiz_question`/the inline `GeneratedQuestion(...)` construction in `questions.py` -- both still run every time, on a hit or a miss, keeping the per-learner row (and its audit trail) exactly as real as it is today.

**Alternatives considered**: A single-slot cache with no pool -- rejected per the spec's resolved clarification (rotating pool of 5, 24h TTL) specifically to avoid many learners seeing the literal identical question indefinitely between version bumps. A separate cache-population background job -- rejected, adds a new execution path (and a Vercel Cron dependency) for no benefit over populating lazily on first request, which is simpler and self-warms exactly the (topic, difficulty) combinations actually being requested.

## §3. Grading-cache lookup and the "same question" key

**Decision**: A new `get_or_grade_answer(db, *, question_stem, rubric_criteria, learner_answer, question_id, learner_id, grading_logic_version, grade_fn, verify_fn) -> tuple[GradingResult, CacheOutcome]` in `backend/src/services/grading_cache/cache.py`, called from `questions.py::_grade_free_text_submission` in place of the direct `grade_free_text_answer(...)` call. The cache key is **not** `GeneratedQuestion.question_id` -- every generated question is its own per-learner row (`generated_question.py:28`, `learner_id` NOT NULL), so two different learners answering "the same" cached-pool question still hold two distinct `question_id`s. Instead: `question_signature = sha256(stem + canonical JSON of rubric_criteria)`, computed once whenever a question is generated (cached or fresh) and stored alongside the `GeneratedQuestion` row's existing fields (no schema change to `GeneratedQuestion` needed -- computed on read from `stem`/`answer_key`, or stored on `question_generation_cache` rows and copied through).

Matching is a **two-stage gate**, not a single embedding-distance threshold (revised 2026-09-02 during `/speckit-implement` Phase 6/T024's live validation against Milestone 6's ground-truth grading eval set -- see below for why the original single-threshold design was disproven): (1) grading-cache rows are matched on `question_signature = :sig AND grading_logic_version = :version`, then ranked by `pgvector` cosine distance between the stored `answer_embedding` and the new answer's embedding (reusing `misconception/embed.py::embed_answer(question_stem, answer_text)` unchanged), narrowing to the single closest row within a loose `PREFILTER_DISTANCE_CEILING` (0.5, efficiency-only -- skips stage 2 entirely for genuinely unrelated answers, never itself a correctness boundary); (2) `equivalence.py::classify_criteria_met` -- a cheap Haiku classification call, same ADK `LlmAgent`+`LiteLlm` pattern as `grading_client/moderation.py` -- re-classifies the new answer against the question's rubric criteria and the candidate is only served as a hit if that classification's `criteria_met` set exactly matches the candidate row's already-stored `criteria_met`. This never compares the new answer against the original learner's raw answer text (FR-009 -- `grading_response_cache` stores none), only against the rubric.

**Rationale**: Once §2's pool is in place, the common case is many learners literally receiving the same cached stem+rubric -- the grading cache only pays off if it can recognize that across their distinct `GeneratedQuestion` rows. A content hash is simpler and more robust than a foreign key to one "canonical" row (which would need inventing given the current per-learner data model), and it also degrades safely: two learners who happen to get independently-generated-but-identical questions (rare, but possible even without the pool) still correctly share a grading-cache entry.

**Similarity threshold -- disproven, superseded by the two-stage gate above**: The original design (0.85 cosine similarity / `<= 0.15` cosine distance as a standalone hit criterion, deliberately matching `dedup/checker.py::is_near_duplicate`'s threshold) was validated live against Milestone 6's ground-truth grading eval set via `backend/scripts/validate_grading_cache_threshold.py` and **failed**: 14 of 19 same-question, opposite-`expected_correct` pairs fell within 0.15 distance (false positives), including the spec's own negation example ("does not require light" vs. "requires light," distance 0.0593) -- and critically, no single threshold value could work at all, since the two genuine true-positive paraphrase pairs measured *smaller* distances (0.0651/0.0789) than several false positives (down to 0.0133). Root cause: `embed_answer(question_stem, answer_text)` embeds the shared, often-longer question stem alongside the answer, so same-question pairs cluster tightly regardless of the answer's actual meaning -- a known general limitation of sentence embeddings on negation, not a bug isolated to this codebase (confirmed: embedding the answer alone, no stem prefix, only partially helps). Resolved via `/speckit-clarify` (spec Clarifications, 2026-09-02): embedding distance now only pre-filters for efficiency (widened to 0.5, since it's no longer a correctness boundary); the rubric-criteria re-classification gate above is what actually resolves the negation case. Re-validated with the real two-stage gate (same script, rewritten to exercise `classify_criteria_met` directly): zero false positives against the full ground-truth set + the negation example, both genuine paraphrase pairs still register as would-be hits. One additional real bug this re-validation caught and fixed: the classifier initially misclassified blank/whitespace answers as satisfying every criterion (a Haiku-specific weakness the full Sonnet-based Grading Agent doesn't share) -- fixed with an explicit blank/off-topic instruction in `equivalence.py`'s prompt.

**Alternatives considered**: Exact-string matching on the answer -- rejected outright by FR-003 (spec requires meaning-based matching). A separate embedding call per grading request with no reuse of `embed_answer` -- rejected, `embed_answer`'s model/env-var/retry shape is already exactly what's needed, duplicating it would violate the "reuse before you write" rung of the ladder for no reason. Storing the original answer text so the equivalence check could compare answer-to-answer directly -- rejected, reverses FR-009's explicit no-raw-text privacy design without a new justification (Constitution Principle VIII); the criteria-pattern re-classification approach needs no raw text at all.

## §4. Audit log and Langfuse trace on a cache hit (FR-013)

**Decision**: No new `AssessmentEventType` member and no new event table. Both `get_or_generate_question` and `get_or_grade_answer` return a `CacheOutcome` (hit/miss + reason, plus the served row's `cache_entry_id` on a hit -- added during implementation once `record_cache_hit_trace`'s metadata need for it became concrete) alongside their real return value; every call site that already builds a payload dict for `record_event(...)` (`questions.py`'s `NEXT_TOPIC_SELECTED` at line ~118, `answer_payload` before `ANSWER_SUBMITTED` at line ~264) adds two keys: `"served_from_cache": bool` and `"cache_miss_reason": str | None`. This is the *entire* new work on the audit-log side -- every `record_event` call already fires unconditionally today, hit or miss, because the per-learner `GeneratedQuestion` row and the graded-answer event are both still written every time (§2/§3). For the Langfuse side: `traced_request()` (`observability/tracing.py`) creates no span itself -- it only propagates metadata onto spans `GoogleADKInstrumentor` creates from a real ADK `Runner` call, and a cache hit makes no such call, so it would otherwise produce *zero* trace. A new `record_cache_hit_trace(*, name, cache_type, cache_entry_id, prompt_version, learner_id)` helper is added to `observability/tracing.py`, using `get_client().start_observation(name=..., as_type="generation", ...)` (Langfuse v4's manual-observation API, `langfuse>=4.14.4` already a dependency -- **correction during implementation**: `start_as_current_generation` does not exist on the installed v4 client; the real one-shot, non-context-manager method is `start_observation(as_type="generation")`, which returns an object ended explicitly via `.end()`) to emit a real generation-shaped span tagged `usage_details={"input": 0, "output": 0}` (zero token cost, since no model call happened) and metadata identifying the original cache entry -- called from both cache-aware wrappers on a hit, inside the same `traced_request()` block the caller already opened.

**Rationale**: Directly resolves the spec's Clarifications (2026-09-02): a cache hit gets a full audit-log entry *and* a full new Langfuse trace, indistinguishable in completeness from a fresh call, per Constitution Principle V's letter ("every agent invocation MUST be traced") applied in spirit even though a cache hit is deliberately *not* a new agent invocation -- the trace exists so "what happened for this specific request" stays answerable, with `usage_details` making the zero-cost, no-model-call nature of a hit visible in Langfuse itself rather than indistinguishable from a real generation there.

**Alternatives considered**: Skipping the Langfuse trace on a hit and relying only on the audit log -- this was Option A in the clarification and was **not** chosen; the user selected full tracing for both. A brand-new `cache_hit`/`cache_miss` `AssessmentEventType` -- rejected as unnecessary schema growth once the payload-flag approach was identified as sufficient; also keeps every existing consumer of `NEXT_TOPIC_SELECTED`/`ANSWER_SUBMITTED` events working unchanged.

## §5. Eviction and freshness

**Decision**: Question-gen pool: enforced entirely at write time (insert a new row, then `DELETE` the oldest row for that exact key tuple beyond the 5th) plus a read-time filter (`created_at > now() - 24h` excludes stale rows from being served, without deleting them). **No Vercel Cron cleanup job in this milestone.** Grading cache: no cap or TTL at all (per spec's Assumptions) -- only a `grading_logic_version` mismatch makes a row unreachable.

**Rationale**: Insert-time eviction alone already bounds question-gen pool growth to `(number of distinct topic/difficulty/content-version/prompt-version combinations ever requested) × 5` -- proportional to the content catalog, not to request volume. Rows for a topic/difficulty combination whose version has since bumped go stale and simply stop being read (§FR-006 already requires this); they don't keep growing because that key tuple's *new* version starts its own fresh pool. A scheduled sweep to physically delete those stale rows would be new operational surface (a new cron route, a new `vercel.json` entry, a new auth-checked endpoint mirroring `cron.py`'s existing pattern) for a problem that's bounded, not unbounded, and that no Success Criterion in the spec measures. Deferred, not overlooked -- worth adding if/when actual storage growth is observed to matter in practice, at which point it's a small, well-precedented addition (`cron.py` already has two examples to copy).

**Alternatives considered**: A Vercel Cron sweep mirroring `/api/cron/classify-misconceptions` -- rejected for now per the above; noted here so a future milestone doesn't have to rediscover the option.

## §6. Grading-cache long-term row growth (flagged, not solved)

Grading-cache rows accumulate indefinitely within a `grading_logic_version` (the spec's own Assumptions accept this: "Grading cache entries don't require a hard row-count/storage cap in this milestone"). This is a known, spec-documented tradeoff, not a plan-introduced gap -- flagged here only so `tasks.md` doesn't need to rediscover it, and so a future milestone considering a cap/eviction policy has a pointer to where the decision was made and why.

## §7. `check_no_subject_conditionals.py` compliance

Both new cache modules read `subject_id`/`topic_id` from function arguments (ultimately sourced from the request/DB), never as a literal string matched against a specific subject. No change needed to the scanner itself; the new modules must simply avoid the anti-pattern it already checks for (Constitution Principle III) -- confirmed as a design constraint on `services/question_cache/cache.py` and `services/grading_cache/cache.py`, not something requiring new tooling.

## §8. No new HTTP API surface

Both cache-aware wrappers are called from *inside* existing route handlers (`questions.py`'s next-question and answer-submission paths, already specified by specs 001/005/007) -- no new endpoint, no changed request/response shape (SC-003 requires this: a caller cannot tell hit from miss from the response). User Story 3's hit-rate visibility is delivered as a maintainer-run script reading `AssessmentEvent.payload` (`served_from_cache`/`cache_miss_reason` keys added in §4), matching this project's existing script-based observability precedent (`batch_eval_questions.py`) rather than a new dashboard or API route.

## §9. Migration shape

One new Alembic migration, chained off `be66baa35493` (the most recent, `generated_question_prompt_version`), creating both new tables in a single revision (`op.create_table` ×2) -- following the existing docstring-cites-spec-and-explains-why convention (`be66baa35493`, `c80b05244e1c`). `pgvector`'s `Vector` column type is already imported project-wide via `pgvector.sqlalchemy.Vector` (`content_passage_embedding.py`), so no new extension-enablement migration is needed (already enabled for that table).

## §10. Synthetic load test (SC-001/SC-002's actual verification mechanism)

**Decision**: `backend/scripts/cache_load_test.py` calls `get_or_generate_question`/`get_or_grade_answer` (research.md §2/§3) directly -- no live server, no HTTP layer -- replaying a configurable volume of repeated/near-duplicate requests across synthetic `learner_id`s, once with caching enabled and once with a `--no-cache` bypass flag, then reports each cache type's hit rate (reusing §8's hit-rate aggregation) and the model-call-volume delta between the two runs.

**Rationale**: `/speckit-analyze` (2026-09-02) flagged that SC-001 ("each cache type independently reaches at least 30%... in a synthetic load test") and SC-002 (measured cost reduction vs. caching disabled) had no task producing the load test they require -- unit/integration tests exercise single request pairs, not volume, and quickstart.md's manual scenarios don't generate enough traffic for a 30%-threshold figure to mean anything. Calling the cache-aware functions directly (rather than driving a real HTTP server) keeps this a fast, dependency-free script in the same spirit as `batch_eval_questions.py --fresh` (Milestone 12) -- no new test infrastructure (no Locust, no separate load-test service), consistent with `tech-stack.md`'s existing testing stack.

**Alternatives considered**: A real HTTP-level load test (e.g. driving `POST /api/questions/next` over the network) -- rejected as unnecessary weight for this milestone's actual question (does the *cache logic* hit its target, not does the *HTTP stack* hold up under load, which is a different, not-yet-asked question).
