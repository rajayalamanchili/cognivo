# Feature Specification: Guardian & Public-Facing UI Redesign

**Feature Branch**: `041-guardian-public-ui-redesign`

**Created**: 2026-10-06

**Status**: Draft

**Input**: User description: "Redesign Home, Sign in, Try the demo, Guardian · My learners, Assigned quiz, and Settings screens to match new design mockups exported from a design tool (purple/lavender palette, Baloo 2 + Nunito typography, pill-shaped buttons/nav, 20-28px rounded cards) -- the same category of work as the prior learner-facing redesign (specs/027-learner-ui-redesign), not a new product capability. Mockup source: six static reference `.dc.html` exports (Home, Sign in, Try the demo, Guardian · My learners, Assigned quiz, Settings), each carrying the exact visual values to replicate in inline styles; markup structure and hardcoded sample data are not meant to be copied as-is."

## Context

Specs/027-learner-ui-redesign restyled the six solo-learner screens (Dashboard, Practice, Mastery, Placement, AI Tutor, Answer Result) to the same purple/lavender, Baloo 2 + Nunito, pill-shaped-button visual language this feature continues. This feature covers the remaining six screens a guardian, prospective user, or an assigned-quiz-taking learner sees: the public Home page, the Sign-in flow, the demo picker, the guardian's "My learners" dashboard, the assigned-quiz start/summary screens, and a guardian Settings page.

Unlike 027 (a near-pure restyle), an investigation of the live app against these six mockups found three of the six screens describe functionality that is only partially built or not built at all:

- **Sign-in** is today a two-page chooser (`frontend/src/app/sign-in/page.tsx` links to separate `(auth)/guardian/sign-in` and `(auth)/instructor/sign-in` pages), not the mockup's single page with a role-tab switcher.
- **Guardian · My learners** (`(auth)/guardian/learners/page.tsx`) exists with an add-learner form, per-learner assignment list, standards/career-connections widgets -- but as a single narrow column, not the mockup's per-learner card dashboard with stat tiles and a grade-band hand-off explainer.
- **Settings** has no guardian-facing page at all today (only a 35-line learner-demo settings page with a single toggle). None of the mockup's Account (edit name/email, change password), Learners (per-learner password reset), or Display/Notification preference-toggle functionality exists in the backend.

The mockups also assume a capability the app deliberately does not have: a real learner login. Investigation confirmed `LearnerProfile` has no credential fields at all (`backend/src/models/learner_profile.py`) and there is no learner `AccountType` (`backend/src/services/auth/tokens.py`). Real learners never log in -- spec 019 (age-adaptive-learner-experience) built a guardian-mediated hand-off instead: the guardian's own authenticated session starts an assignment attempt (`backend/src/services/quiz_assignment/assignment.py`'s `start_assignment_attempt`), which mints a short-lived, quiz-session-scoped `quiz_handoff` JWT (`tokens.py`'s `issue_handoff_token`). That token is returned in the same HTTP response and kept in the starting browser tab's React state (`frontend/src/components/LearnerAssignments.tsx`) -- there is no email, link, QR code, or code-entry field that delivers it to a genuinely separate device. "The learner continues on their device" means the guardian hands over the same device/tab they started it on, not that a second device discovers a waiting quiz.

This context directly shaped the Clarifications below: rather than building a new learner-credential system or implying a cross-device capability that doesn't exist, this feature matches the mockups' visual design to the app's real, already-decided architecture wherever the two conflict, and closes the three screens' genuine functional gaps using already-available data wherever possible (same standard 027 applied), adding real backend only where the mockup's own content (Settings' Account/Learners/Notifications sections) has no existing feature behind it at all.

A fourth gap surfaced during clarification, not from the mockups themselves but from how "join a class" actually works today: joining requires a join code an instructor must hand a guardian out-of-band, with no in-app way to find a class otherwise (`enrollment.py`'s `join_roster` looks a roster up strictly by that code; nothing lists rosters across instructors). This feature adds a guardian-facing class directory to close that gap (FR-017-FR-021) -- a genuinely new, instructor-opt-in capability, not implied by any mockup, scoped narrowly enough (one new field on each of two existing entities, one new read endpoint, one new instructor-side toggle) to fit alongside this redesign's other gap-closing work rather than needing a separate spec.

A fifth gap surfaced while scoping the free-practice entry point above: investigation found that `practice-flow.tsx` isn't uniquely demo-hardcoded -- `dashboard-flow.tsx`, `mastery-flow.tsx`, `tutor-flow.tsx`, and the shared `Nav.tsx` all call `getDemoLearner()` unconditionally too, with no real-learner-context mechanism (no context/provider, no URL param) anywhere in the frontend. Of spec 027's six redesigned screens, only the assigned-quiz flow works for a real learner today, and only because `LearnerAssignments.tsx` is a separate component that never goes through `quiz-flow.tsx` at all -- it takes a real `learnerId` prop directly and reuses the same learner-agnostic presentational components (`QuestionCard`, `QuizSummary`) that the demo-hardcoded flow wrappers also use. This feature extends that same already-proven pattern to Dashboard, Practice, Mastery, and AI Tutor (FR-016) -- no new backend (every page already has, or already reuses, a real-learner-ownership-gated endpoint), but a real frontend code change across five existing files, not mere wiring.

## Clarifications

### Session 2026-10-06

- Q: The mockups' Sign-in screen has a Learner tab, and "Add a learner" has username/password fields -- both imply a guardian creates a real login for their child, which doesn't exist and isn't the app's design (see Context). How should the redesign handle this? → A: Drop both. Sign-in ships with Guardian/Instructor tabs only (2-way, not 3-way). "Add a learner" keeps today's name-only field. This matches the app's real, deliberate architecture -- not a gap to close, a mockup assumption that doesn't fit how this product actually works.
- Q: The Settings mockup's Account section (edit name/email, change password), Learners section (per-learner "reset password"), and the six Display/Notification toggles have no backend today at all -- no account-update endpoint, no password-change/reset endpoint, no preference-storage table. (Privacy & data's delete flows are already backed by the real spec 020 deletion-request API, so those wire up for free.) How much new backend should this feature build? → A: Build it all -- guardian account-edit (name/email), change-password, per-learner password-reset, and one small preference-storage surface for the six toggles, so Settings is fully functional, not a restyled mockup of nothing.
- Q: The Assigned-quiz start screen's mockup banner reads "Your guardian started this quiz for you. It's ready on this device" -- which implies the learner finds it waiting on their own, separate device. The real mechanism (Context) is same-device/same-tab hand-off only; no cross-device delivery exists. Keep the literal copy, or reword it to match reality? → A: Reword to match reality (e.g. "Your guardian started this quiz -- continue below"). Everything else on that screen (stat tiles, "results come at the end" notice, Begin button) restyles as-is, since it doesn't depend on which device is in use.
- Q: Can the mastery before→after shown on the Assigned-quiz summary screen ("mastery 48% → 63%") be built from data already fetched, with no new backend? → A: Yes, confirmed by investigation -- `QuizAnswerResultOut` (`backend/src/api/routes/quiz.py`) already carries both `prior_p_mastery` and `posterior_p_mastery` per question, mirrored in the frontend's `QuizAnswerResultEntry` type (`frontend/src/services/api.ts`) and already returned by the same endpoint the assigned-quiz summary uses. Showing a per-topic before→after requires only grouping the already-fetched `per_question_results` by topic and taking each topic's first `prior_p_mastery` and last `posterior_p_mastery` -- pure client-side aggregation, zero new fetch.
- Q: The mockup's "Join a class" form suggests enrolling in a subject is a separate step from joining a class, and a not-yet-enrolled learner's card shows "Placement not taken" as its focus text -- does this redesign need a new subject-enrollment action, and does it need to wire up a real placement flow for guardian-managed learners (today, placement is demo-learner-only infrastructure -- `backend/src/api/routes/placement.py` resolves the learner via `get_demo_learner()` with no real-learner path at all, and real learners already practice and take assigned quizzes without it)? → A: No new work on either count. `ClassroomRoster.subject_id` is a mandatory, non-nullable FK (`backend/src/models/classroom_roster.py`) -- joining a class *is* enrolling in that class's subject; there is no separate subject-only enrollment path to build. Real placement stays demo-only; this feature does not wire it up for real learners (that would be new product scope, the same category of decision as the declined real-learner-auth option above). The "working on" stat tile (FR-008) sources from the next-topic recommendation for any enrolled learner regardless of whether a placement step ever ran; a learner not yet in a class shows "Not in a class yet" rather than the mockup's literal "Placement not taken" text (Assumptions).
- Q: How does a real learner start free (non-assigned) practice today, and should this redesign add that entry point? → A: Investigation found the backend already supports it (`GET /api/learners/{learner_id}/next-question` in `backend/src/api/routes/questions.py` already calls `require_learner_ownership_if_real`, the same gate `mastery`/`activity-summary`/`recommendation` endpoints use) but the frontend's `/practice` page (`practice-flow.tsx`) hardcodes `getDemoLearner()`, so no real learner can start practice today -- a standing gap, not something this redesign created. Despite the mockup showing no "Start practice" control (only assigned quizzes + join-class), this feature adds one to each learner card on Guardian · My learners, passing the real `learner_id` to the already-ownership-gated endpoint -- no new backend, pure frontend wiring, closing a real gap while it's already in view.
- Q: "Join a class" requires a join code today (`enrollment.py`'s `join_roster` looks a roster up strictly by `join_code`; there is no roster-listing or roster-ID-based join path anywhere -- `GET /api/rosters` is instructor-scoped only). Can a guardian join a class without the instructor separately handing them a code? → A: Not today, and that's a real gap worth closing, not existing behavior to merely preserve: add a guardian-facing class directory. A guardian can browse real instructors' publicly-listed, open-enrollment classes and join one directly, with no code to type or receive out-of-band.
- Q: Should every registered instructor's open-enrollment roster be listed in this new directory by default, or must an instructor explicitly opt a roster in? → A: Opt-in. An instructor explicitly marks a roster "listed" for it to appear; closed (approval-required) rosters are never listed regardless of this flag, preserving their existing code-only privacy model. This protects instructors who create a roster expecting the join code itself to be the access boundary, the same deliberate default this feature chose for the earlier real-learner-auth and real-placement questions (add real capability only where it closes a clear gap without silently changing an existing privacy boundary).

### Session 2026-10-06 (second pass)

- Q: Dashboard, Mastery, and AI Tutor share Practice's exact gap -- all four (plus the shared Nav) are hardcoded to the demo learner, with zero real-learner access today. Should this feature extend real-learner access to all four, or stay limited to the "Start practice" entry point already scoped? → A: Extend to all four. A guardian opens one real-learner session per learner (landing on Dashboard, the same default the demo learner gets) from Guardian · My learners; from there, the existing Dashboard/Practice/Mastery/AI Tutor navigation (already shared via `Nav.tsx`) carries that same real learner's context between pages, exactly mirroring how the demo-learner bucket already works. FR-016 is corrected accordingly: this is a real frontend code change to five existing files (four flow components plus `Nav.tsx`), not "pure frontend wiring" -- still zero new backend, since every page's data need is already covered by an existing real-learner-ownership-gated endpoint (`mastery-state`, `activity-summary`, `recommendations`/`topic-priority-preview`, `next-question`, and the Tutor Agent's own existing endpoint).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A visitor, guardian, instructor, or learner sees the refreshed visual design with no change in existing behavior (Priority: P1)

Anyone viewing Home, Sign-in, the demo picker, Guardian · My learners, or the Assigned-quiz screens sees the new purple/lavender visual language -- pill-shaped buttons and nav, rounded cards, the updated palette and type treatment -- while every interaction that already works today (starting the demo, signing in, joining a class, starting an assigned quiz, viewing a graded result) behaves exactly as it did before, aside from the two deliberate, clarified departures from the mockups (no Learner sign-in tab; the hand-off banner's reworded copy).

**Why this priority**: This is the entire point of the redesign for everything that's already real. A visual update must never silently change or break working functionality.

**Independent Test**: Load each of the six screens before and after the redesign with the same guardian/instructor/demo state and confirm identical data, navigation targets, and interactive outcomes, with only visual presentation (and the two clarified copy/scope departures) differing.

**Acceptance Scenarios**:

1. **Given** the Home, Try the demo, Guardian · My learners, and Assigned-quiz screens, **When** each renders, **Then** its colors, typography, spacing, corner radii, and button/nav shapes match the corresponding mockup's values.
2. **Given** Sign-in, **When** it renders, **Then** it is a single page with a two-way Guardian/Instructor tab switcher (not the mockup's three-way), each tab showing its current id-field label, redirect target, contextual note, and registration availability exactly as today's separate pages already define them.
3. **Given** a guardian on Guardian · My learners, **When** they join a class, add a learner, or start an assigned quiz for a learner, **Then** the outcome (roster state, learner list, quiz session start, guardian-mediated hand-off behavior) is identical to today's behavior.
4. **Given** the Assigned-quiz start screen, **When** it renders, **Then** its guardian-hand-off banner describes same-device continuation (not cross-device pickup), per Clarifications.
5. **Given** a screen or component outside the six named screens, **When** the redesign ships, **Then** its layout, component shapes, and structure are unchanged, except for shared color-token values that cascade site-wide by design (same precedent as spec 027's Clarifications).

---

### User Story 2 - A guardian manages their account, their learners' logins, their preferences, and their privacy from one real Settings page (Priority: P1)

A guardian visits Settings and can: edit their own name/email and change their password; see each learner they manage; toggle accessibility and notification preferences that persist across visits; and submit or review a learner-data-deletion request or their own account-deletion, using the mockup's new visual design. (The mockup's per-learner "reset password" row has nothing to act on -- learners have no credential of their own, per Clarifications -- so it is dropped rather than shipped as a non-functional control.)

**Why this priority**: Without this, Settings would be a restyled page with non-functional controls -- worse than not shipping it, since it would look interactive while doing nothing. The guardian-facing privacy controls in particular (Constitution Principle VIII) must be real, not decorative.

**Independent Test**: As a guardian, edit account details, toggle each preference, reload the page, and confirm the edits and toggle states persisted; submit a learner-deletion request and confirm it reaches the existing spec 020 deletion pipeline with a real pending status.

**Acceptance Scenarios**:

1. **Given** a guardian on Settings' Account section, **When** they edit their name or email and save, **Then** the change persists and is reflected on reload.
2. **Given** a guardian on Settings' Account section, **When** they change their password, **Then** they can subsequently sign in with the new password and not the old one.
3. **Given** a guardian on Settings' Display & accessibility or Notifications sections, **When** they toggle a preference (read-aloud, larger text, reduce motion, theme, practice reminders, quiz-finished email, weekly summary), **Then** the new state persists across a page reload and a new session.
4. **Given** a guardian on Settings' Privacy & data section, **When** they request deletion of a learner's data or their own guardian account, **Then** the request is submitted to the existing deletion-request flow (spec 020) and its pending/completed status is shown, matching that flow's existing guarantees.
5. **Given** the "Add a learner" form (on Guardian · My learners), **When** a guardian submits it, **Then** it still only requires the learner's name, with no username/password fields (Clarifications).

---

### User Story 3 - An assigned-quiz summary shows mastery before and after, built from data already on hand (Priority: P2)

A learner finishing an assigned quiz sees, for each topic the quiz covered, their mastery estimate before the quiz and after it, alongside the existing score and per-question Met/Missed rubric breakdown.

**Why this priority**: A real, useful piece of the mockup's summary screen, but lower priority than Stories 1-2 because it enhances an already-functional screen rather than fixing a non-functional one, and because the underlying data already exists (Clarifications) -- it's a presentational addition, not a new capability.

**Independent Test**: Complete an assigned quiz covering a known topic, and confirm the summary screen's before→after mastery value for that topic matches the topic's `prior_p_mastery` on the first question answered and `posterior_p_mastery` on the last question answered for that topic, with no new network request beyond what the summary screen already fetches.

**Acceptance Scenarios**:

1. **Given** an assigned-quiz summary covering one or more topics, **When** it renders, **Then** each topic shows a before→after mastery value derived from that topic's first `prior_p_mastery` and last `posterior_p_mastery` already present in the fetched `per_question_results`.
2. **Given** the same summary screen, **When** it renders, **Then** no additional network request is made beyond what today's summary screen already fetches.

---

### User Story 4 - A guardian opens a real learner's full learning experience, not just an instructor-assigned quiz (Priority: P2)

A guardian on Guardian · My learners opens one real-learner session per enrolled learner, landing on that learner's Dashboard, with Practice, Mastery, and AI Tutor all reachable from there via the same shared navigation the demo learner already uses -- closing a standing gap where none of spec 027's four non-quiz screens have ever worked for a real learner.

**Why this priority**: Real learners today have no way to see their own dashboard, practice freely, check mastery, or ask the AI Tutor -- only instructor-assigned quizzes work for them, even though every one of these pages already has a real-learner-ownership-gated backend endpoint to call (Clarifications). A real, pre-existing gap, not introduced by this feature, but surfaced and closed while this exact page was already being rebuilt. Lower priority than Stories 1-2 because it's additive, not a fix to something broken or non-functional.

**Independent Test**: As a guardian with an enrolled learner, open that learner's session from their card and confirm Dashboard renders that real learner's own mastery/activity data (not the demo learner's); from there, navigate to Practice, Mastery, and AI Tutor via the shared nav and confirm each stays scoped to the same real learner, with no new backend call introduced to support any of the four.

**Acceptance Scenarios**:

1. **Given** a guardian with an enrolled, real learner, **When** they open that learner's session from their card, **Then** Dashboard renders scoped to that real learner's own `learner_id`, using the same already-ownership-gated endpoints (`mastery-state`, `activity-summary`, `recommendations`/`topic-priority-preview`) Guardian · My learners' own stat tiles (FR-008) already call.
2. **Given** a guardian inside a real learner's session, **When** they navigate to Practice, Mastery, or AI Tutor via the shared nav, **Then** each page stays scoped to that same real learner (not the demo learner), using its own existing ownership-gated endpoint, with no new backend call added to support any of the four.
3. **Given** a guardian inside a real learner's session, **When** the shared `Nav` renders, **Then** it shows that real learner's own identity (e.g. their name), not the demo-account badge -- the badge is reserved for the actual demo learner (Constitution Principle VIII) and must never appear for a real learner's data.
4. **Given** a learner not yet enrolled in any class, **When** their card renders, **Then** no session-entry action is shown (mirroring the existing `needsClass` case, since there is no subject context for a dashboard, practice, or mastery view to scope to yet).
5. **Given** a guardian ends a real learner's session (returning to Guardian · My learners) and then opens a different learner's session, **When** the second session starts, **Then** it is scoped to the second learner only -- no bleed-through of the first learner's identity or data into the second.

---

### User Story 5 - A guardian finds and joins a class without needing a code from the instructor (Priority: P2)

A guardian with a learner who isn't in a class yet can browse real instructors' publicly-listed, open-enrollment classes (by subject, grade, instructor name) and join one directly from Guardian · My learners, as an alternative to typing a join code an instructor shared with them separately.

**Why this priority**: Closes a real, user-facing gap (today, "join a class" is only possible if a guardian already has a code from the instructor) that surfaced directly from scoping this exact form. Lower priority than Stories 1-2 because it's a genuinely new capability, not a fix to something broken, and the directory starts empty until at least one real instructor registers and opts a class in -- not a regression, just an honest bootstrap state.

**Independent Test**: As a guardian with a learner not in any class, open the "join a class" section, browse listed classes, pick one, and confirm the learner ends up enrolled (or pending approval, if the directory ever lists a roster requiring it -- it won't, per Clarifications) exactly as if they'd typed that roster's join code.

**Acceptance Scenarios**:

1. **Given** at least one real instructor has registered, created an open-enrollment roster, and explicitly listed it, **When** a guardian opens "join a class," **Then** that roster appears with its subject, grade, and instructor's display name, and no join code is shown or required.
2. **Given** a guardian selects a listed class and confirms, **When** the join completes, **Then** the learner is enrolled in that roster with the same outcome as today's code-based open-roster join.
3. **Given** no instructor has listed any roster yet, **When** a guardian opens "join a class," **Then** the directory shows an empty state (not an error), and the existing code-entry field remains available as before.
4. **Given** a closed (approval-required) roster, **When** the directory renders, **Then** that roster never appears in it, regardless of any listing flag (Clarifications) -- closed rosters stay code-only.
5. **Given** an instructor has not opted a roster into the directory, **When** a guardian browses the directory, **Then** that roster does not appear, even if its enrollment mode is open.

---

### Edge Cases

- A guardian with zero learners added yet: Guardian · My learners renders the "add a learner" sidebar prominently with no learner cards, not an error state.
- A learner not yet in any class: their card shows the "join a class" form, an empty assigned-quizzes list, and "Not in a class yet" as its focus text (not the mockup's literal "Placement not taken," since placement doesn't exist for real learners -- Clarifications), not a broken stat-tile row (mirroring the mockup's `needsClass` case).
- A guardian changes their password: any other active session for that guardian should not silently keep working under the old credential in a way that undermines the point of changing it.
- A guardian requests deletion of a learner who has an in-progress assigned quiz: the existing spec 020 deletion-authorization rules govern this; the redesign must not introduce a new path that bypasses them.
- A screen state the mockups don't depict (empty, loading, error) on any of the six screens must still render using the new design tokens.
- The shared `Nav`/header component spans both redesigned (guardian) and not-yet-redesigned (instructor) surfaces; only the shared color-token cascade applies to the latter, not new layout/shape (same rule as spec 027).
- An instructor roster that is both closed and listed (an invalid combination -- Clarifications): the system must not allow setting "listed" on a closed roster, rather than silently ignoring the flag.
- A real instructor has never set a display name (registered before this feature, or skipped it): the directory must not show a blank or raw-ID instructor identity -- a display name is required at registration (FR-017) going forward, and existing accounts are prompted to set one before any of their rosters can be listed.
- Two guardians attempt to join the same listed, open roster for their respective learners at the same time: both succeed independently, identical to today's concurrent-join behavior for a shared code (no new race condition introduced).
- A real learner's session must never display the demo-account badge, and the demo learner's own Dashboard/Practice/Mastery/AI Tutor must continue to show it exactly as before -- the two identities (demo vs. a specific real learner) must never be conflated by `Nav` or any of the four flow components.
- A guardian opens a real learner's session, then opens Settings or signs out without explicitly returning to Guardian · My learners first: the real-learner session must end cleanly (not persist into a subsequent, unrelated page view) -- same guarantee Story 4's fifth acceptance scenario already requires between two different learners' sessions.
- A guardian with more than one enrolled learner: each learner's session is independent and does not expose, or require closing, any other learner's session first.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The Home, Sign-in, Try the demo, Guardian · My learners, and Assigned-quiz (start and summary) screens MUST visually match the provided design mockups' color palette, typography, spacing, corner radii, and component shapes, except where FR-004/FR-005/FR-006 below deliberately depart from the mockup.
- **FR-002**: The redesign MUST NOT alter grading, mastery-model, sequencing, roster/enrollment, or guardian-mediated hand-off logic on any of the six screens, except for the narrowly-scoped class-directory addition permitted by FR-017-FR-021 and the real-learner-session data-source change permitted by FR-016/FR-022 (which changes which learner's data a page fetches, never the mastery-model, grading, or sequencing logic those endpoints already run). Display-level data composition MAY change where needed to match the mockups: prefer consuming a value already returned by an existing API response over fetching something new, and prefer a new client-side derivation from already-fetched data over a new network call, in that order (same standard as spec 027).
- **FR-003**: Every already-shipped behavior on these screens -- joining a class, adding a learner by name, starting an assigned quiz via guardian hand-off, the per-question Met/Missed rubric breakdown, the persistent demo-account badge, standards/career-connections widgets -- MUST continue to function identically after the redesign.
- **FR-004**: Sign-in MUST be restyled as a single page with a two-way Guardian/Instructor tab switcher (not the mockup's three-way Learner/Guardian/Instructor), reusing each role's existing id-field label, redirect target, contextual note, and registration availability. No Learner tab, and no real learner-credential sign-in, is introduced (Clarifications).
- **FR-005**: "Add a learner" MUST remain a name-only form. No username or password field for the learner is introduced (Clarifications) -- consistent with FR-004 and the Context's finding that real learners never log in by design.
- **FR-006**: The Assigned-quiz start screen's guardian-hand-off banner MUST describe same-device/same-tab continuation, not cross-device pickup (Clarifications) -- the mockup's literal "It's ready on this device" framing is replaced with wording that doesn't imply a delivery mechanism that doesn't exist.
- **FR-007**: The Assigned-quiz summary screen MUST show, for each topic the quiz covered, a before→after mastery value computed client-side from that topic's first `prior_p_mastery` and last `posterior_p_mastery` already present in the existing quiz-summary response's `per_question_results` (Clarifications) -- no new backend field or endpoint.
- **FR-008**: Guardian · My learners' per-learner stat tiles (topics mastered, this week, working on) MUST be derived from existing per-learner endpoints already gated for guardian-owned real learners (`mastery-state`, `activity-summary`, `recommendations`/`topic-priority-preview`, all already authorized via `require_learner_ownership_if_real`) -- no new fetch beyond calling these with the guardian's own real learner IDs instead of the demo learner's. The "working on" tile sources from the next-topic recommendation for any enrolled learner regardless of whether a placement step ever ran (Clarifications) -- this feature does not build a real-learner placement flow.
- **FR-009**: Settings MUST provide a real, persisted Account section: a guardian can view and edit their name and email, and change their password, with changes taking effect for future sign-ins.
- **FR-010**: Settings' Learners section MUST list each learner the guardian manages (name, grade, class). It MUST NOT include a "reset password" control -- per FR-004/FR-005, learners have no credential of their own to reset.
- **FR-011**: Settings MUST provide real, persisted Display & accessibility preferences (read-aloud default, larger text, reduce motion, theme) and Notifications preferences (practice reminders, quiz-finished email, weekly summary) per guardian, surviving reload and new sessions.
- **FR-012**: Settings' Privacy & data section MUST wire its "delete a learner's data" and "delete my guardian account" actions to the existing spec 020 deletion-request API, showing that request's real pending/completed status -- no new deletion logic is introduced, only a UI for the existing one.
- **FR-013**: Shared visual values (color, type scale, spacing, radii) introduced by the redesign MUST be defined in the project's existing shared design-token system (the same one spec 027 established), not duplicated as one-off literal values per component.
- **FR-014**: Screens and components outside the six named screens are out of scope for layout, component-shape, and structural changes, which MUST NOT change as a side effect of this redesign, with the same shared-color-token-cascade exception spec 027 established, and two narrow functional exceptions: FR-018 on the instructor roster-creation screen, and FR-016/FR-022 on spec 027's Dashboard, Practice, Mastery, and AI Tutor screens (and the shared `Nav`) -- none of these four gain any visual/layout change under this feature, only real-learner-session data-awareness.
- **FR-015**: The redesign MUST introduce no new database table or backend surface beyond what FR-009/FR-011/FR-012 require (guardian account-edit, change-password, and one minimal preference-storage surface for the six toggles) or FR-017/FR-019 require (instructor display name, roster listing flag, and the directory-listing capability) -- no other new backend surface is permitted under this feature.
- **FR-016**: Each enrolled learner's card on Guardian · My learners MUST include an action, alongside the existing assigned-quizzes list, that opens a real-learner session for that learner, landing on Dashboard, with Practice, Mastery, and AI Tutor reachable from there via the existing shared navigation -- not present in the mockup, added to close a standing gap (Clarifications): none of spec 027's four non-quiz screens has any real-learner entry point today. This requires replacing the unconditional `getDemoLearner()` call in each of `dashboard-flow.tsx`, `practice-flow.tsx`, `mastery-flow.tsx`, `tutor-flow.tsx`, and the shared `Nav.tsx` with real-learner-session awareness (mirroring the pattern `LearnerAssignments.tsx` already proved for assigned quizzes) -- a real frontend code change across five existing files, not mere UI wiring. No new backend endpoint is introduced: each page's data need is already covered by an existing real-learner-ownership-gated endpoint (`mastery-state`, `activity-summary`, `recommendations`/`topic-priority-preview`, `next-question`, and the Tutor Agent's existing endpoint).
- **FR-017**: Real instructor registration MUST collect a display name, persisted on `RealInstructorAccount`, shown wherever an instructor's identity is surfaced to a guardian (the class directory, FR-019). An existing real instructor account with no display name MUST be prompted to set one before any of their rosters can be listed (Edge Cases).
- **FR-018**: The instructor roster-creation/management screen (out of scope for this redesign's visual changes, per FR-014) MUST gain exactly one new control: a "List in directory" toggle, settable only on an open-enrollment roster. Setting a roster to closed MUST clear this flag (or the system MUST reject closing a currently-listed roster without first un-listing it) -- a roster MUST NOT be both closed and listed (Edge Cases).
- **FR-019**: Guardian · My learners' "join a class" section MUST offer a browsable directory of real instructors' open-enrollment rosters that have been explicitly listed (FR-018), showing each roster's subject, grade, and instructor display name (FR-017), alongside the existing code-entry field -- not replacing it.
- **FR-020**: Selecting a listed roster from the directory and confirming MUST produce the identical enrollment outcome as joining that same roster via its join code today (an active `Enrollment`, no approval step, since closed rosters are never listed) -- the directory is a discovery and selection convenience, not a second enrollment code path with different semantics.
- **FR-021**: Closed (approval-required) rosters MUST NOT appear in the directory under any configuration (Clarifications, Edge Cases) -- their existing code-only, approval-gated privacy model is unchanged.
- **FR-022**: While a real learner's session (FR-016) is active, `Nav` MUST display that real learner's own identity and MUST NOT display the demo-account badge; the demo learner's own Dashboard/Practice/Mastery/AI Tutor sessions MUST continue to show the badge exactly as before (Edge Cases). A real-learner session MUST end cleanly on return to Guardian · My learners, sign-out, or switching to a different learner's session, with no identity or data bleed-through between sessions (Edge Cases).

### Key Entities

- **Guardian preference**: A per-guardian record of the Display & accessibility and Notifications toggle states (read-aloud default, larger text, reduce motion, theme choice, practice-reminder opt-in, quiz-finished email, weekly summary). New in this feature (FR-011); no existing entity covers it.
- **(No new entity for Account edit/change-password)**: these act on the already-existing `RealGuardianAccount` record's existing name/email/password-hash fields -- no new table, just new write paths.
- **(No new entity for deletion or mastery before→after)**: both reuse existing entities (`DeletionRequest`, `AssessmentEvent`/`per_question_results`) read-only or via the existing deletion flow, per FR-007/FR-012.
- **(No new entity for the real-learner session, FR-016/FR-022)**: the session is an ephemeral client-side/request-scoped concern (Assumptions), not a persisted record -- no new table.
- **Instructor display name**: a new, required-going-forward attribute of the existing `RealInstructorAccount` entity (FR-017) -- not a new entity, a new field on an existing one.
- **Roster listing flag**: a new boolean attribute of the existing `ClassroomRoster` entity (FR-018), mutually exclusive with closed enrollment mode (Edge Cases) -- not a new entity, a new field on an existing one.

## Assumptions

- The six exported design files are reference mockups: static HTML with hardcoded illustrative sample data. Their exact sample copy and numbers are not literal content requirements -- only their visual values (color, type, spacing, radii, shapes) are, except where Clarifications explicitly call out a copy change (FR-006).
- Baloo 2, Nunito, and the shared design-token system are already established by spec 027; this feature introduces no new font or third-party dependency, so `tech-stack.md` needs no amendment.
- This is a visual-design-system update bundled with closing pre-existing, already-decided functional gaps (guardian account management, preference persistence, wiring the existing deletion API to a UI) -- not a new product capability in the Constitution's sense (no new agent, no new personalization/grading logic). Consistent with spec 027's own precedent, it does not add an entry to `roadmap.md`'s milestone sequence.
- No real learner credential system is introduced by this feature (Clarifications); the mockup's per-learner "reset password" row is deliberately omitted (FR-010) rather than shipped as a non-functional control, since no learner credential exists for it to act on.
- The guardian preference entity (new Key Entity) is scoped to the guardian, not per-learner, matching the mockup's single, unkeyed toggle rows -- except "practice reminders," which the mockup shows named per learner ("Practice reminders for Eli"); the exact schema (guardian-wide vs. per-managed-learner) is left to `/speckit-plan`'s data-model design, not fixed here.
- Settings' Account change-password flow reuses whatever password-hashing mechanism `register_guardian`/`login_guardian` (`backend/src/api/routes/auth.py`) already use -- no new hashing scheme is introduced.
- "Enroll in a subject" and "join a class" are the same action, not two steps (Clarifications): `ClassroomRoster.subject_id` is a mandatory FK, so there is no subject-only enrollment path to design a UI for.
- Real placement for guardian-managed learners is out of scope (Clarifications) -- it remains the demo-learner-only capability it is today. This is a deliberate scope boundary, not an oversight: real learners already practice and take assigned quizzes without it.
- Real-learner access to Dashboard, Practice, Mastery, and AI Tutor (FR-016/FR-022) is a deliberate, scoped exception to this feature's otherwise restyle-first bias (Clarifications): none of the four is shown as a Guardian · My learners action in the mockup, but every one of them already has a real-learner-ownership-gated backend endpoint, and the gap (no real learner can reach any of the four today) was surfaced while scoping this exact page -- closing it costs real frontend code changes across five existing files, but zero new backend.
- A single entry point per learner card opens the real-learner session (landing on Dashboard), rather than four separate buttons for Dashboard/Practice/Mastery/AI Tutor -- this mirrors exactly how the demo learner already reaches all four from one entry point via the shared `Nav`, and keeps Guardian · My learners' card layout from growing a button per screen. `/speckit-plan` owns the exact session mechanism (e.g. a URL param, a route-scoped context, or reusing `Nav`'s existing `demoLearnerMode`-style localStorage pattern) -- this spec fixes the product behavior (one real learner's identity flows across all four pages until the session ends) without mandating the implementation.
- The class directory (FR-017-FR-021) starts empty in any environment with no real, opted-in instructor -- this is an honest bootstrap state, not a bug, and SC-008's test requires seeding at least one real instructor with a listed roster to exercise. No demo-labeled synthetic instructor is created to pre-populate it (Constitution Principle VIII's demo-flagging rule governs any such account if one is ever added, and this feature does not add one).
- The directory is read-only discovery over existing join semantics (FR-020): it does not introduce a second way to enroll with different rules, only a second way to find a roster_id/join_code pair without typing it. `/speckit-plan` decides the concrete mechanism (e.g. the directory response carrying the roster's join_code for listed rosters, reusing the existing code-based join call under the hood, vs. a new roster_id-based join endpoint) -- both satisfy FR-020's "identical enrollment outcome" requirement; this spec does not mandate one over the other.
